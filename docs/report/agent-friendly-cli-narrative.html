What Makes a Command-Line Tool Easier for AI Agents to Use?

I wanted to understand a simple question:

What makes a command-line tool easy for an AI agent to use?

The tool I studied is botmap, a command-line interface for querying map data. An AI agent receives a question in plain English and access to a shell. It has to figure out which commands to run, interpret the results, recover from mistakes, and eventually answer the question.

I recorded every command the agent ran, every result it saw, how long it took, and whether it eventually reached the right answer.

Study based on botmap commit 3009509 · baseline: 60 attempts · generated from the project’s recorded runs. Dataset and traces on Hugging Face ↗

The first surprise: “did it error?” is a weak test

I needed a way to judge whether the tool helped or hindered that process. A simple success/error check missed important behavior. Some failed commands were useful because they explained what to try next. Some commands succeeded while returning incomplete or misleading results.

Baseline: 500 tool calls

Most calls were clean. Silent wrong answers were the largest single failure category.

silent wronghard failureguided failure

Across the baseline run, there were 111 failure instances. 55 of them were silent failures: the command looked successful and still misled the agent. A conventional “did the command error?” test would have missed every one of them.

Two problems dominated those silent failures. In 25 cases, the tool returned only part of a long list and the agent read it as complete. In another 25, the tool returned an empty result without enough information to explain why.

Then the measurement itself became the problem

I ran the unchanged tool several times on exactly the same five evaluation questions. Because nothing had changed, the starting score should have been roughly the same each time.

The unchanged system scored anywhere from 0.576 to 0.764.

That is a spread of 0.187 caused by the agent behaving differently from run to run. The automated improvements I measured later were +0.006 and +0.016—far smaller than that natural variation.

It is like weighing something on a scale that swings by two kilograms and then announcing a sixty-gram improvement. The improvement might be real. This particular measurement cannot show it convincingly.

This changed how I interpreted the optimizer runs. Their curves are useful for understanding how the search behaved. Their final heights provide weak evidence for small improvements.

Across the three optimizer runs, 186 evaluations produced only nine candidates that received a full test. Seven of those nine scored worse than the version they started from. The broadest search had 83 editable files and only a handful of serious evaluations—a very large search space for a very small budget.

The targeted fixes were much easier to learn from

Instead of asking, “Can this change improve one overall score?”, I tried a narrower question: “Does this particular failure stop happening?”

That made both the engineering and the measurement more concrete.

Why the targeted approach worked better

The automated optimizer was being asked a broad question: “Can you make the overall score better?” That is hard when the overall score itself moves substantially between identical runs.

The targeted experiments started from something more concrete: “Agents keep making this specific mistake.” From there I could ask what change might prevent that mistake, then test that change only where it was relevant.

The difference is visible in the measurements:

  • Automated search: +0.000, +0.006, +0.016 on an overall score whose observed run-to-run spread was 0.187.
  • Targeted fixes: 13 → 5, 2 → 0, 3 → 0, 25 → 1 for specific, observable failures.

These samples are too small to establish that every intervention will generalize. They make what changed, why it changed, and which behavior to inspect next much clearer.

What I would change in the next run

  • Measure natural variation first. Run the unchanged system repeatedly before spending evaluation budget on proposed improvements.
  • Keep the editable area small. The four-file optimizer run was more promising than the 83-file run.
  • Route tests by failure. If a change targets incomplete lists, evaluate it primarily on the attempts where incomplete lists caused trouble.
  • Use larger samples for claims. A 2 → 0 or 3 → 0 result over four attempts can easily be coincidence.
  • Improve diagnostics before optimization. Twenty-five of the 55 silent failures are still unexplained empty-result cases. A generic “unknown” bucket is too vague for an optimizer—or a person—to target well.

The larger takeaway

Make failures visible before trying to optimize them away.

The most useful loop in this study was: observe how agents fail → group similar failures → understand the cause → make a small targeted change → test it on the cases it was meant to fix.

For this project, a small search feature aimed at one recurring source of confusion reduced its target failure from 25 cases to 1. That was much easier to trust and reason about than a tiny movement in a noisy aggregate score.

The broader lesson is straightforward: to make software easier for AI agents to use, first make their failures understandable.
