Evaluator design

  • Tool under test: botmap, a CLI over Overture map data — multiple resource types, domain vocabulary, structured filters, ambiguous place names, large/expensive outputs.
  • Task: the agent gets a plain-English question and a shell, nothing else. Every command, output, token count, timing and final answer is recorded.
  • Why the naive scorer ("did it error?") was replaced: it punished helpful error messages and rewarded silent zero-result answers — a clean exit code is not the same thing as a correct answer.

Failure taxonomy

  • Class A — Hard / unguided failure: usage error, raw traceback, no usable way forward (attribution penalty 1.00)
  • Class B — Guided / recoverable failure: command fails but names a usable next step (attribution penalty 0.10)
  • Class C — Silent wrong: command succeeds or looks plausible, but misleads the agent (attribution penalty 1.00)
  • Class D — Degenerate route: works, but via a needlessly broad or expensive path (attribution penalty 0.45)
  • Class E — Environment / quota failure: excluded entirely — never charged to the CLI (not charged to the CLI)
  • Class F — Agent-side failure: e.g. an ignored hint — recorded, not charged to the CLI (not charged to the CLI)

Class C is further split by subtype: c-truncated (a capped list read as complete), c-unknown (an unexplained empty result), c-wrong-type (right filter, wrong resource type), c-wrong-column (right filter, wrong field). Figure 0 below shows how the baseline's 111 failure instances split across these.

Scoring rubric — how the 100 points split

  • 60/20/20 means an agent-friendly CLI is graded mostly on whether the agent could recover, not on how fast or cheap the attempt was.
  • The 60 correctness points split into 5 scoring components, not the 4 failure classes: final outcome 20, self-recovery 20, guidance quality 12, route quality 6, attribution 2.
  • Failure-class severity (the A/B/C/D penalties above) only feeds into attribution — the smallest slice, 2 of 100 points. Class B is charged at just 0.10 because a guided failure is mostly forgiven once the agent uses the guidance to recover.

Guardrails

  • Differential probes: a suspicious zero (e.g. --where subtype=bicycle_parking → 0) is re-tested under a related filter before it is trusted as a real absence.
  • Sabotage gate: known-bad fixtures for every class/subtype must be caught before an optimizer run is allowed to start.
Terms used on this page (glossary)
TermWhat it means
rubric scoreA grade from 0 to 1 that the evaluator gives one attempt at one question. Higher is better. 60% of it is about whether the agent recovered from trouble, not just whether it got the answer.
held-out setFive questions kept aside and never used to guide the optimizer, so we can check it learned something general rather than memorising the practice questions.
candidateOne proposed edit to the tool or its instructions. The optimizer invents these, then has to decide whether to pay to test each one.
minibatchA cheap 3-question screening test. A candidate must beat its parent here before it earns a full, expensive test on all five held-out questions. This is why most iterations cost nothing and the line stays flat.
evaluationOne grading of one candidate. The budget was 60 evaluations — not 60 iterations and not 60 questions. The runs actually spent 61 to 63.
iterationOne round of: propose a change, screen it cheaply, maybe test it fully. A single iteration can burn several evaluations, which is why a budget of 60 evaluations bought only 8 or 9 iterations — that is the whole x-axis of Figure 1.
attemptOne agent trying one question once. Every question is run twice, so the baseline's 60 attempts are 30 questions run twice, not 60 questions.
callOne botmap command run inside an attempt. The baseline's 60 attempts contain about 500 calls, and it is calls that get classified.
failure instanceOne call classified as a failure. Figure 2 counts these, not attempts. One attempt can contain several, which is why Exp 4's 25 instances live in only 13 attempts.
failure subtypeA named way the agent got it wrong — for example c-truncated means a list was silently cut short, so the agent read a partial answer as a complete one. Figure 2 counts these instead of scoring them.

Read this first: the measuring instrument wobbles more than anything it measured. All three runs started from the untouched tool and were graded on the same five questions — the code that picks them, questions.split(), always picks the same ones. Those five were hardware-near-bikepaths, pharmacies-monaco, street-canonical-form, unsupported-hours-and-ratings, which-admin-areas. So the three starting scores should have been identical. They were not: they came out 0.5764 to 0.7637, a gap of 0.187 caused by nothing but the agent behaving differently each time. That gap is the size of the wobble. It is 31× bigger than Arm C's +0.006 (almost certainly noise, not a real gain) and 12× bigger than the narrow tool run's +0.016. It is like weighing yourself on a scale that swings by two kilos and announcing you lost sixty grams — the loss may be real, but this scale cannot see it. Read the curves below for their shape, not their height.

Reading across the arms

Figure 1 asks "did the score go up?" Figure 2 asks "did this specific failure stop happening?" The second question got useful answers; the first mostly did not — that gap is the real finding.

Why the optimizer arms barely moved

  • The ruler was coarser than what it measured: three runs of the unchanged tool scored 0.187 apart — bigger than every optimizer gain on this page.
  • The budget bought very few real looks: 186 evaluations across all three runs produced only 9 fully-tested candidates, and 7 of those scored worse than the base they started from. Arm C had ~0.7 evaluations per editable file — not a search, a coin toss.
  • A bigger edit surface made search worse, not better: Arm C (83 files) spent its best patch on .gitignore; the narrow run (4 files) produced the biggest optimizer gain on the page (+0.0161).
  • Optimizers spotted the problem but couldn't build the fix: both GEPA arms noticed agents struggling to discover category names, but turned it into longer instructions (Arm B) or an unwritten suggest.py note (Arm C). Arm E turned the same signal into one working command, botmap categories --search TERM, moving its target failure 25 → 1.

What actually improved

  • Exp 1 — truncation warning: 13 → 5 on 6 attempts.
  • Exp 2 — wrong-column hint: 2 → 0 on 4 attempts.
  • Exp 3 — wrong-type hint (Arm D): 3 → 0 on 4 attempts, only 2/4 completed — provisional.
  • Exp 4 — categories --search (Arm E): 25 → 1 across every affected attempt — the strongest, most trustworthy result in the study.
  • tool-narrow (GEPA, 4 files): +0.0161 — the only optimizer gain, and it still sits inside the 0.187 noise band.

What went wrong this round

  • The wobble was never measured directly — the 0.187 spread comes from 3 accidental data points, not a designed noise run. A 60-attempt repeat run exists but recorded failure kinds, not the score each time.
  • Arm A screened on everything instead of what mattered — all 60 attempts per candidate; two of three enrichments timed out, one run halted at 37/60.
  • The evaluator itself had a bug for part of the run — US state codes and country codes were confused (Cambridge, MA vs. Malta, MT); fixing it changed the failure distribution.
  • Some results shipped on samples too small to trust: Exp 3 moved 3 → 0 on 4 attempts, only 2 finished.

What to change in the next run

  • Measure the wobble first: run the unchanged tool 10–20× before spending budget on candidates; require gains to clear ~2× the standard deviation.
  • Fewer files, more looks: the 4-file run beat the 83-file run.
  • Route by failure class from the start — test a candidate only on the attempts it targets, the way Arm E did.
  • Raise the minimum sample size — Exp 2 and Exp 3 tested on just 4 attempts each; 4 attempts cannot separate a fix from a coincidence, unlike Exp 4's full 13-attempt affected subset.
  • Mine rejected optimizer proposals deliberately — the discards (zero-result diagnostics, place-name normalisation, a suggestions module) were as valuable as the accepted patches.
  • Fix instrumentation debt first: 25 of 55 silent-wrong instances (45%) are still unexplained (c-unknown) — nothing can target that bucket until better probes split it up.
